最近，我把面向威胁狩猎与应急调查的项目 [ThreatHuntingAtlas](https://github.com/stevenpsm/ThreatHuntingAtlas) 开源了，中文名是“企业关键系统失陷狩猎图谱”。它将目标系统、失陷场景和证据来源关联起来，帮助调查人员确定排查方向、梳理采集清单，并记录当前证据的缺口。

它处理的问题很具体：怀疑一台服务器、一个应用或者一套基础设施被入侵之后，应该从哪里查起？哪些日志要先保全，哪些配置需要一起拿走，眼前的线索又能支持什么判断？

项目采用离线交付方式，将调查知识和交互功能封装在一个 HTML 文件中，下载后用浏览器打开即可。使用者可以围绕具体系统和怀疑场景，关联查看历史漏洞、证据来源及调查步骤，再整理成一份 Markdown 狩猎计划。

本文对应 `v0.1.1`。下面的中文演示展示了从目标系统进入详情，查看历史漏洞和日志证据的过程。英文演示可在[项目 README](https://github.com/stevenpsm/ThreatHuntingAtlas#readme) 中查看。

## 从“看看日志”往下多走一步

“查一下访问日志、登录日志、异常进程。”这句话当然没错，但落到具体系统上，还有不少问题没有回答。

访问日志具体写在哪里？有没有覆盖所有虚拟主机？请求经过反向代理后，后端的执行过程能否追到？某个审计功能现在已经打开，事发时是否也开着？日志只保留了三天，而可疑活动发生在一周前，这份材料又能说明多少？

ThreatHuntingAtlas 想把这些细节放到调查入口附近。选中一个系统后，除了看到可能的失陷形态，还能继续查到对应的日志、文件、配置、进程和网络证据，以及这些材料的适用条件。

例如，“Web 服务器”只是一个起点。Nginx、Apache HTTP Server、IIS 的日志机制和部署方式有区别。即便都是 Nginx，安装在 Linux 主机上，和作为 Kubernetes Ingress Controller 运行，需要保全的材料也有区别。调查清单需要落到具体产品和部署条件上。

## 拿 Nginx 走一遍

假设收到一条线索：某个对外 Web 服务出现了可疑请求，入口使用 Nginx，暂时不清楚有没有造成实际影响。下面只是使用示例，不对应真实事件。

打开图谱后，可以从目标系统卡片进入 **Nginx 与 Apache HTTP Server**，再查看 Nginx 的产品级证据条目。如果已经有较明确的怀疑方向，也可以进入“攻击与痕迹矩阵”，查看这个目标与 RCE、WebShell、持久化等场景之间的关系。

这里先别急着把可疑请求套进某个 CVE。对这个例子，我会先核对下面几件事：

| 要核对的问题 | 对应材料 | 容易漏掉的细节 |
| --- | --- | --- |
| 请求到底经过了哪里？ | 主配置、全部 include、虚拟主机和代理配置 | 命中哪个 server/location，是否转发给了后端应用 |
| 请求日志是否完整？ | 实际配置的访问日志及轮转文件 | 日志可能按站点拆分、条件记录，也可能输出到 syslog 或容器日志 |
| 请求期间服务发生了什么？ | 错误日志、已有的 WAF 审计记录、后端应用日志 | 不同层的时间和请求标识能否关联；WAF 记录是否实际存在 |
| 有没有执行或落地的迹象？ | 应用相关目录、文件元数据、进程及连接证据 | 要结合实际部署确定执行进程和目录，不能仅凭入口组件推断 |

图谱里的 Nginx 条目会进一步提示：访问日志应按实际的 `access_log` 配置寻找；日志路径和格式可以自定义；代理场景下还要检查现有 `log_format` 是否记录了 `$upstream_addr`、`$upstream_status` 等变量。

这个细节很实际。看到清单里写着“上游信息”，不代表磁盘上一定有一份单独的 upstream 日志。事发时没有记录的字段，事后改配置也补不回来。

同样，Nginx 出现在链路入口，不足以说明漏洞就在 Nginx。假如它后面代理的是一个 Java 应用，后续调查就需要把 Java 平台以及相应进程、应用日志纳入范围。工具里的目标可以组合选择，调查范围也应该随着证据调整。

等这些基本情况明确后，再看历史漏洞和特征会更有意义：先核对组件、版本、补丁与触发条件，再找时间上能够关联的执行、文件或网络变化。可疑请求说明有人尝试过什么，是否成功还需要其他材料支撑。

## 把缺口写进狩猎计划

查阅资料之后，可以进入“狩猎计划”，选择目标系统、具体产品和怀疑场景，标记目前掌握的证据，再生成并导出 Markdown。

我比较在意这里对证据状态的区分：已经掌握、部分掌握、缺失、未知，应当分开记录。

比如，拿到了最近一天的访问日志，但调查窗口是三天；有进程列表，却没有事发时的进程创建记录；知道有集中日志平台，但还没确认该资产是否接入。这几种情况都不适合简单打一个“已采集”的勾。

界面会显示证据掌握度。这个百分比只用于提醒材料准备到了什么程度，不能用来估计失陷概率。拿齐日志后仍然可能没有足够证据支持结论；拿不到日志，也不能据此排除攻击。

导出的计划适合继续补充调查时间范围、采集人、保全位置、分析结果和待办事项。工具负责提供一份有上下文的起点，最终记录仍然需要跟着现场情况走。

## 把系统、失陷场景和证据关联起来

图谱以目标系统和失陷场景为入口，连接具体产品、历史漏洞、日志与证据工件，以及对应的检测和调查方法。沿着这些关系，可以从“怀疑发生了什么”继续查到“应该保全哪些材料”，再核对这些材料的适用条件和判断边界。

这些关系落实在每一条产品证据记录中：采集优先级、适用条件、来源位置、使用限制，以及关联的证据类别和失陷场景。前面提到的 Nginx 日志路径、部署条件和字段限制，就是其中的例子。查阅一个条目时，可以同时了解去哪里找、什么情况下能找到，以及拿到后能说明什么。

当前版本整理了 16 类目标系统、38 个具体产品身份和 375 条产品级最低日志与证据条目；另外包含 13 类失陷形态、21 个代表性历史漏洞、44 类具体证据工件和 29 份防御性狩猎配方。这些数字描述的是当前内容规模，实际使用时仍要逐项确认适用性。

## 离线使用，无需部署

项目将知识数据、界面和交互逻辑一并封装，检索、关系展示、计划生成和文件导出都在浏览器本地完成。把文件带到分析环境，打开就能查，不需要部署服务、安装数据库或者申请账号，正常使用也不依赖远程脚本、字体或数据接口。查阅原始参考资料时，再按需要打开外部链接。

目前支持中文和英文。右上角可以切换，也可以在文件地址后加上 `?lang=en` 打开英文界面。

离线版本中的知识内容随 Release 更新。使用时需要留意版本，下载新版才能获得后续修订；遇到具体产品的版本适用性问题，仍应对照条目所引用的原始资料核验。

## 使用时保留一点克制

图谱中的历史漏洞和协议指纹都只能提供调查线索。产品名称相同、版本看起来接近，或者命中一条特征，都需要继续核对适用条件和独立证据。尤其是协议指纹，离开资产角色、进程归属和时间关系，单独拿出来很容易被过度解释。

工具不会连接目标主机、执行命令或自动采集证据。里面的狩猎配方需要由使用者检查参数、权限、执行环境和可能产生的影响，再决定如何使用。浏览器里的计划也不能代替证据保全记录、专业解析工具或者完整的取证过程。

当前主要测试环境是 Linux 上的 Chromium，其他浏览器和受管环境还需要更多验证。知识内容也有覆盖不全、表述不够准确的地方。比起单纯增加条目，我更希望先把已有条目的条件和边界写清楚。

希望下次面对一个不太熟悉的系统时，这张图谱能帮你少漏掉一份该保全的材料，也更清楚地写出：现在知道了什么，还有什么没查到。
