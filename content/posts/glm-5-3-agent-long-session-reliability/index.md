最近，我通过 pi coding agent 使用 GLM-5.3，完成了一次超过 60 轮的长会话。任务不是单点写代码，而是连续跨过需求讨论、代码修改、测试、后台任务、部署和进展汇报。

这段经历给我的感受有些矛盾。

一方面，GLM-5.3 确实能够处理复杂代码和长链路任务。官方也把复杂编码和 long-horizon agentic tasks 作为这个版本的重要方向。另一方面，会话越长，我越明显地看到一些并非“这段代码不会写”的问题：它会选择性汇报进展，会被更有趣的新任务吸引，会在没有查证时判断功能不存在，也会用环境限制解释自身实现中的缺口。

这些问题单独看都不惊人。真正麻烦的是，它们会在长任务里互相加强：未验证的判断触发重复开发，重复开发引入回归，回归又被正向汇报掩盖；一个已经得到批准的小任务，则可能在不断出现的新想法中被推迟很多轮。

我不想只留下一句“这个模型有时不可靠”。于是把这次会话中的问题整理成六类模式，并尝试把缓解措施压缩成可以放进 Agent 上下文的执行规则。

## 先说明：这不是一份模型测评

[GLM-5.3 官方项目](https://github.com/zai-org/GLM-5)把它描述为更擅长复杂编码和长时程任务的版本。这篇文章不试图反驳相关基准，也不比较不同模型的智力排名。

我的样本只是一段真实但未经控制的长会话。结果同时受到模型版本、推理预算、上下文压缩、pi 的 Agent Loop、工具权限、项目复杂度以及我的提示方式影响。观察到某种行为，不足以证明根因一定在模型，更不能直接推出“所有 LLM 都这样”。

因此，下面使用“模式”这个词，只表示同类问题在这段会话的多个阶段反复出现。对于根因，我保留假设；对于缓解效果，则需要后续用对照实验验证。

这也是我后来决定建立独立知识库的原因：把现场观察、通用假设、运行时指令和验证结果分开保存，避免经验很快变成未经检验的教条。

## 六类反复出现的问题

### 一、选择性汇报：完成了多少，却不说总共有多少

Agent 很容易给出令人满意的进展描述：“完成了 46 个”“测试全部通过”“覆盖从 0 增长到 23”。这些数字未必是假的，问题在于缺少分母和结论边界。

`46/83` 与“完成 46 个”给人的感觉不同；某个测试套件全绿，也不等于用户的系统目标已经完成。增量很大，绝对覆盖仍可能很低。

我最后加入了一条很朴素的汇报契约：坏消息先于好消息，完成量必须带分母，并严格区分命令成功、测试通过、功能实现和系统目标达成。分母不知道时，不能省略，而要明确写“分母未知”。

### 二、兴趣驱动跳转：新架构总比补参数更有吸引力

在多个待办同时存在时，Agent 会明显偏爱探索性工作。搭一个新框架、设计一套新流水线或者接入新工具，很容易获得持续注意；补参数、更新文档和修小 bug 则会一次次留到后面。

最典型的情况是，用户已经明确说了“同意，做吧”，Agent 也表示记住了，但下一轮又被新的复杂问题吸引。

缓解方法不是再次强调“请认真完成”，而是维护显式队列：`approved / active / blocked / done`。用户批准的事项立即进入最高优先级，在完成或明确阻塞前，不启动无关的新工作。同时限制在制任务数量，避免 Agent 用不断立项制造进展感。

### 三、未验证断言：把“没看到”说成“不存在”

长会话里出现过几次类似判断：某功能“还没有实现”，实际却已经存在于独立脚本中，只是没有接入当前入口；早期讨论过的组件，在很多轮以后又被建议重新开发。

这里最重要的修正，是区分五种状态：不存在、已实现但未集成、已集成但未启用、已启用但未验证、已经验证。它们不能都被一句“没有”代替。

我把“先查再答”写成了强制规则。凡是涉及功能存在性或当前状态的断言，必须先搜索、读取配置或运行只读探测。用户说“我记得已经有了”时，第一反应也应该是重新查证，而不是维护上一轮回答的一致性。

### 四、盲等与未来承诺：等待并不等于监控

后台任务运行时，Agent 有时会直接选择一个很长的 `sleep`。如果任务在第一秒就失败，剩余时间只是盲等；如果任务已经挂起，只检查进程是否存活也发现不了问题。

另一类问题是承诺“几分钟后我会再检查”。这是否能够兑现，取决于 Agent Harness 有没有定时唤醒或持续监控机制。没有调度能力时，这句话只是看起来体贴，实际上必须等待下一条用户消息才能继续。

更可靠的方式是：任务启动后立刻检查一次，优先等待明确的完成条件；必须轮询时设置短间隔、硬上限和取消方式，同时检查错误、存活状态与进展增量。连续两次没有增量，就从“继续等待”转入“排查是否挂起”。

### 五、归因偏差：先怪环境，再看自己的代码

当一个动作失败时，“环境不支持”“工具不兼容”“系统设计如此”都是很方便的解释。但有些问题最终只是适配器少了一个 handler、参数格式传错，或者已有实现没有接入当前入口。

我把故障归因拆成固定顺序：先排查实现缺陷，再排查集成缺口，最后才判断外部环境限制。前两层没有用证据排除时，就不能把第三层写成结论。如果确实还不知道，写“尚未定位”比选择一个听起来合理的原因更诚实。

### 六、修复引入回归：目标用例绿了，整体指标却下降了

Agent 修 bug 时很容易只盯住触发问题的那个用例。替换一个共享 handler 后，原问题通过了，另一个消费者却失去能力；直到下一次全量测试，才发现总体指标比修复前更差。

缓解方法包括变更前列出消费者、保存修改前基线、先跑目标回归，再根据影响面运行相称的测试集合。对于高风险共享组件，应执行全量测试；对于局部低风险修改，可以记录理由后使用缩小的回归范围。

我没有把“一切修改无条件跑全量测试”写成通用规则。那会把可靠性要求变成昂贵而容易被绕过的仪式。更可执行的原则是：测试范围必须与风险相称，所有新增失败都要解释。

## 为什么不直接把长文改名为 AGENTS.md

[pi coding agent](https://github.com/earendil-works/pi)可以从全局或项目目录加载 `AGENTS.md`。最初我的想法也是把六类问题和全部分析直接写进去。

但重新审视后，我觉得这不是一个好结构。

研究文档需要保存观察背景、根因假设、反例和证据限制；运行时上下文需要的是短、明确、可检查的动作。把两者混在一起，不但浪费上下文，还可能让真正重要的指令淹没在解释中。

因此我建立了一个新仓库：[Agent Reliability Patterns](https://github.com/stevenpsm/agent-reliability-patterns)。仓库不绑定单一模型，而是把内容分成五层：

```text
cases/       脱敏后的现场案例与证据
patterns/    完整的模型与 Harness 观察记录
guardrails/  可注入 system prompt 或 AGENTS.md 的短规则
evals/       可重复运行的对照评测
templates/   后续模型复现与对照实验模板
```

首篇观察文档命名为：

```text
patterns/glm-5.3-pi-long-session-failure-modes.md
```

真正适合复制到项目上下文的内容，则放在：

```text
guardrails/long-session-reliability-guardrails.md
```

这个拆分还有一个好处：未来如果同一模式在其他模型中没有复现，不需要修改一份假装通用的 `AGENTS.md`，只要更新模式的证据状态即可。

## 护栏不能只看起来合理

Prompt 工程里一个常见陷阱，是写出一组非常正确的规则，然后默认问题已经解决。模型能够复述“先查再答”，不等于下一次真的会先查。

我准备为这些护栏记录一组更直接的指标：

| 指标 | 想回答的问题 |
| --- | --- |
| 分母完整率 | Agent 报告完成量时，有多少次同时给出总量？ |
| 欠账可见率 | 已知失败项有多少出现在主摘要，而不是附录？ |
| 批准任务账龄 | 用户同意后，过了多少轮才真正执行？ |
| 查证先行率 | 存在性断言中，有多少附带搜索或探测证据？ |
| 零进展发现延迟 | 后台任务挂起多久以后才被发现？ |
| 归因证据率 | 故障结论是否依次排除了实现和集成问题？ |
| 回归逃逸率 | 修复引入的新失败，有多少没有在提交前发现？ |

后续验证至少要固定模型版本、推理预算、Harness 版本、上下文策略、工具权限和任务输入，再比较有无护栏时的表现。否则，一次变好可能只是模型采样差异，一次变差也可能来自上下文压缩或工具环境。

## 我真正想积累的，不是模型吐槽

这次整理最初来自对 GLM-5.3 的使用体验，但我不希望仓库最后变成不同模型的缺点清单。

更有价值的问题是：哪些失败能够稳定复现，哪些来自特定 Harness，哪些可以通过上下文契约缓解，哪些必须依靠外部状态机、测试系统或产品机制解决。

有些约束适合写进 Prompt，例如汇报必须带分母；有些约束更适合交给机器，例如自动生成覆盖指标和回归差异；还有些能力必须由 Harness 提供，例如定时唤醒、持久化待办和后台任务事件。不能把所有工程责任都塞回模型上下文。

一次 60 多轮的会话不足以给出通用答案，但足以让我开始建立一套更可验证的记录方式。与其期待 Agent 永远记住“要更可靠”，不如让每一种可靠性要求都有明确的触发条件、可观察信号和失败门禁。

这大概也是我使用长时程 Agent 之后最直接的感受：模型能力决定它有可能走多远，而任务状态、验证机制和工程护栏，决定它走远以后还记不记得自己为什么出发。
